\section{Reproducibility}

We ran the study from a clean checkout with Python 3.14.7, Docker Engine
29.8.0, Docker Compose 5.5.1, and GNU Make. After starting Docker, we
installed the pinned Python dependencies, ran \texttt{make setup}, and checked
that the replica set had one primary and two secondaries. We then ran the
configuration campaign, followed by the fault campaign and the small matched
mechanism replay. These are the commands at the repository root:

\begin{verbatim}
python3.14 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements-dev.txt
make setup
make experiment
make rq2
make rq3-preflight
make rq3
\end{verbatim}

The campaigns record one history per trial. We recomputed the classifications
from those histories with \texttt{make analyse}, \texttt{make rq3-analyse}, and
\texttt{make rq4-analyse} before compiling the PDF. A smoke or pilot run can
check a new installation, but neither belongs to the reported totals.

The repository retains the deployment, schedules, histories, and offline
checks. The submitted archive contains the compiled PDF and the MongoDB
runtime code, but not the authored LaTeX, tests, saved histories, or report
builder. Appendix~\ref{app:install} gives the remaining validation commands;
Appendix~\ref{app:full-results} holds the detailed matrices. The prose is
maintained directly in LaTeX; the build inserts numeric results from saved
histories without generating report text.
