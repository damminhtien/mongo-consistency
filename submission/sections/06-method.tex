\subsection{Trial model and consistency checkers}

Each trial uses a fresh document, one PyMongo client session, and a
property-specific test schedule. Increasing application versions and write
identifiers make dependencies visible in the recorded history. We log the
requested member and responding server, together with concern settings,
session state, operation status, timing, and returned document state.

A separate fault controller applies and removes each fault. After recovery, a
post-recovery observer reads all three members without reusing the test
client's session. Offline checks compare the client-returned versions for RYW
and MR, verify that W1's identifier appears in W2's atomic pre-image for MW,
and compare R1's returned version with W2's pre-image for WFR. The observer
records whether acknowledged writes remain and whether all members agree on
the final update list; we report these durability observations separately.

\subsection{Configuration campaign}

To isolate the effect of the settings, we run the same four schedules across
all eight configurations. We first run normal controls, then deliberately
create replica divergence for the adversarial histories. Three repetitions
per configuration and property form
\(3\times8\times4=96\) normal controls. Five repetitions form
\(5\times8\times4=160\) adversarial histories, for 256 histories in total.
Smoke and pilot histories are kept separate.

Each schedule creates the observation needed for its property:

\begin{description}
\item[RYW] Keep a secondary at version 0, acknowledge a write of version 1
through the client, and read from the stale secondary.
\item[MR] Isolate a secondary at version 0. If the other secondary is chained
through it, direct that member to replicate from the primary with
\texttt{replSetSyncFrom}~\cite{mongodb-replset-syncfrom} and verify the source
change. After a majority-acknowledged seed write, read version 1 from the fresh
secondary and then read from the stale secondary in the same client sequence.
\item[MW] Write on an isolated branch, allow the majority side to elect, and
issue a successor write after the topology change.
\item[WFR] Read a version on an isolated branch, wait for the majority-side
election, and issue a dependent write on the new primary.
\end{description}

In the fault campaign, MR creates a majority-acknowledged seed write outside
the client session and requires the first client read to return version~1
before the fault. For WFR, F1 and F2 also use a majority-acknowledged setup
write, regardless of the client settings, before reading version~1.
F3 isolates the former primary,
creates the setup write with \texttt{w:1}, verifies version~1 on that branch
and version~0 on the majority side, and then reads version~1 before the
election. In every case, W2 is issued only after R1 has returned a concrete
version.

Schedules issue a dependent operation only after all prerequisites pass and
any required version is recorded.

\subsection{Fault campaign}

We select C1, C3, C4, and C6 for the fault campaign because they include a
weak baseline, two partial settings, and the majority-read/majority-write
causal setting. We cross them with the four property schedules and three
faults. F1 stops one secondary. F2 stops the primary, waits for the remaining
members to elect, and then resumes the scheduled calls. F3 blocks replication
between the former primary and the other two members while preserving the
test client's route to the isolated member. This last case separates a
client-visible old branch from the majority side.

The core design contains \(4\times3\times4\times8=384\) histories. Four F3
configuration-property cells receive twelve additional repetitions each, giving
\RQTwoHistoryCount\ histories across \RQTwoFaultEpisodeCount\ shared fault
episodes. Histories in one episode share a topology event; the episode is the
fault-injection unit. Matching normal controls provide the descriptive baseline.

\subsection{Outcome classification and measurements}

Each history is classified as PASS, VIOLATION, UNAVAILABLE, INDETERMINATE,
PRECONDITION\_MISS, or HARNESS\_ERROR. A history is PASS or VIOLATION only
when the operations required by its property complete and provide sufficient
evidence. UNAVAILABLE records a required operation that did not complete;
INDETERMINATE records an unresolved write effect or missing checker evidence,
such as a required write pre-image. A received response can coexist with an
INDETERMINATE result when a write effect or required evidence remains
unresolved. PRECONDITION\_MISS
marks a history that stopped before its intended test; HARNESS\_ERROR marks an
invalid harness execution. The consistency denominator includes PASS,
VIOLATION, UNAVAILABLE, and INDETERMINATE histories; precondition misses and
harness errors are excluded.

Tables abbreviate these outcomes as P (PASS), V (VIOLATION), U (UNAVAILABLE),
I (INDETERMINATE), PM (PRECONDITION\_MISS), and HE (HARNESS\_ERROR).

For a set of histories, the resolved violation rate is
\[
V=\frac{\#\mathrm{VIOLATION}}
        {\#\mathrm{PASS}+\#\mathrm{VIOLATION}}.
\]
The decidable-history rate is
\[
D=\frac{N_{\mathrm{PASS}}+N_{\mathrm{VIOLATION}}}
        {N_{\text{all valid trials}}}.
\]
For the critical operation in the test schedule, the operation completion rate is
\[
C=\frac{N_{\text{critical operation completed}}}
        {N_{\text{critical operation issued}}}.
\]
An issued operation has a record in the history; it is completed when the
record says a response was received, whether success or a server error. C is
undefined when no critical operation was issued.

The client-operation success rate is
\[
S=\frac{\text{successful client operations}}
        {\text{attempted client operations}}.
\]

All-attempt latency includes timed-out operations when their durations are
available. Resolved latency uses PASS and VIOLATION histories. Table~3 reports
all-attempt p50 and p95; Appendix~C reports all-attempt and resolved p95.
