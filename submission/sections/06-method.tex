\subsection{Trial model and consistency checkers}

Each trial uses a new document so its tested version comes from that trial.
The subject uses one explicit PyMongo session and a
sequence chosen for one property. Increasing application versions and write
identifiers make its dependencies visible in the record. We log the requested
member and the responding server to identify which copy supplied each value.
The record also includes concern
settings, session state, operation status, timing, and returned document state.

After each trial, an independent observer reads the members without the
subject's session. A separate controller applies and removes the fault. Our
offline checker first asks whether the intended operations took place. For
RYW and MR it compares values returned to the subject. For MW it checks
whether W1's identifier was in the atomic pre-image of W2; for WFR it compares
the value read by R1 with W2's pre-image. We apply the course definitions in
Section~2.1 to these recorded observations.

The post-heal observer records whether acknowledged writes remain after
recovery and whether replicas agree on the final update list. We report these
durability observations separately from the client-centric consistency outcome.

\subsection{Configuration campaign}

To isolate the effect of the settings, we run the same four schedules across
all eight configurations. We first run normal controls, then deliberately
create replica divergence for the adversarial histories. Three repetitions
per configuration and property form
\(3\times8\times4=96\) normal controls. Five repetitions form
\(5\times8\times4=160\) adversarial histories, for 256 histories in total.
Smoke and pilot histories are kept separate.

Each schedule creates the observation needed for its property:

\begin{description}
\item[RYW] Keep a secondary at version 0, acknowledge a write of version 1
through the subject, and read from the stale secondary.
\item[MR] Isolate a secondary at version 0. If the other secondary is chained
through it, direct that member to replicate from the primary with
\texttt{replSetSyncFrom}~\cite{mongodb-replset-syncfrom} and verify the source
change. After a majority-acknowledged seed write, read version 1 from the fresh
secondary and then read from the stale secondary in the same client sequence.
\item[MW] Write on an isolated branch, allow the majority side to elect, and
issue a successor write after the topology change.
\item[WFR] Read a version on an isolated branch, wait for the majority-side
election, and issue a dependent write on the new primary.
\end{description}

In the fault campaign, MR creates a majority-acknowledged seed write outside
the subject session and requires the first subject read to return version~1
before the fault. For WFR, F1 and F2 also use a majority-acknowledged setup
write, independent of the subject configuration, before reading version~1.
F3 isolates the former primary,
creates the setup write with \texttt{w:1}, verifies version~1 on that branch
and version~0 on the majority side, and then reads version~1 before the
election. In every case, W2 is issued only after R1 has returned a concrete
version.

Schedules issue a dependent operation only after all prerequisites pass and
any required version is recorded.

\subsection{Fault campaign}

We select C1, C3, C4, and C6 for the fault campaign because they include a
weak baseline, two partial settings, and the majority-read/majority-write
causal setting. We cross them with the four property schedules and three
faults. F1 stops one secondary. F2 stops the primary, waits for the remaining
members to elect, and then resumes the scheduled calls. F3 blocks replication
between the former primary and the other two members while preserving the
subject client's route to the isolated member. This last case separates a
client-visible old branch from the majority side.

The core design contains \(4\times3\times4\times8=384\) histories. Four F3
signature cells receive twelve additional repetitions each, giving
\RQTwoHistoryCount\ histories across \RQTwoFaultEpisodeCount\ shared fault
episodes. Histories in one episode share a topology event; the episode is the
fault-injection unit. Matching normal controls provide the descriptive baseline.

\subsection{Outcome classification and measurements}

Each history is classified as PASS, VIOLATION, UNAVAILABLE, INDETERMINATE,
PRECONDITION\_MISS, or HARNESS\_ERROR. Only PASS and VIOLATION are decidable
consistency outcomes. UNAVAILABLE records a failed client operation, while
INDETERMINATE records an unresolved effect or dependency.
PRECONDITION\_MISS identifies a history that stopped before the intended test;
HARNESS\_ERROR identifies an invalid harness execution.

For a set of histories, the resolved violation rate is
\[
V=\frac{\#\mathrm{VIOLATION}}
        {\#\mathrm{PASS}+\#\mathrm{VIOLATION}}.
\]
The decidable outcome rate is
\[
D=\frac{\#\mathrm{PASS}+\#\mathrm{VIOLATION}}
        {\#\mathrm{PASS}+\#\mathrm{VIOLATION}
        +\#\mathrm{UNAVAILABLE}+\#\mathrm{INDETERMINATE}}.
\]
The subject-operation success rate is
\[
S=\frac{\text{successful subject operations}}
        {\text{attempted subject operations}}.
\]

D measures how often classified histories yield a decidable consistency
outcome. We report p50 and p95 operation latency, retain timed-out
operations in all-attempt samples when their times are available, and use
PASS/VIOLATION histories for resolved samples.
