\section{Method and fault model}

The runner separates subject operations, diagnostic observations, topology
faults, and offline checking. Each trial uses one explicit PyMongo
ClientSession. Causal ON and causal OFF differ only in the session option.
Direct-member diagnostic clients never use the subject session.

The logical state is one document $x$ with an append-only list of integer
versions. Every operation records the requested member and actual command
server. The actual role is obtained from a direct member observation and
timestamped; the driver's cached role is logged separately. Session
$clusterTime$, operationTime, command concerns, afterClusterTime, fault state,
latency, and error classification are retained when available.

RYW isolates a secondary, verifies that it is reachable at $v_0$, writes $v_1$
on the primary, proves the fresh/stale split, then reads the stale secondary.
MR isolates the stale secondary before its setup write, verifies the fresh/stale
split, and performs fresh then stale reads in one subject session. MW isolates
the old primary before subject W1, verifies W1's actual route, elects a new
primary, and issues dependent W2 through the same session. WFR writes $v_1$
directly to the isolated old branch with $w:1$, reads a concrete version through
the subject session, elects a new primary, and issues W2 only if that concrete
dependency exists.

After a fault, the controller heals the network and the topology oracle must
observe one primary and two secondaries. An independent observer then reads the
complete document from all three members. MW/WFR checkers require a stable
topology and identical, valid member snapshots.

The operation deadline is 5 seconds; the election/topology barrier is 30
seconds and a trial is limited to 60 seconds. Retry reads and writes are
disabled. A write timeout after the command may have reached MongoDB is
INDETERMINATE. A missing schedule state is PRECONDITION\_MISS, not a database
failure.

The design uses a 32-history machinery smoke, a separate 192-history pilot,
and a sequential RQ1 campaign of 320 controls plus 960 adversarial histories.
The smoke and pilot are not included in RQ1 estimates.

RQ2 crosses C1, C3, C4, and C6 with secondary crash (F1), primary
crash/election (F2), and primary-isolating network partition (F3), using RYW,
MR, MW, and WFR in every cell. RQ1 normal histories for the same four
configurations and properties provide the descriptive baseline; RQ2 adds no
normal histories.

There are eight core repetitions per cell: 3 faults x 8 repetitions x 4
configurations x 4 properties = 384 histories. Four F3 signature cells
(C1/C6 x RYW/MW) extend from eight to 20 repetitions, adding 48 histories. The
registered RQ2 total is 432 histories. The execution groups each fault and
repetition into one episode: 24 core episodes contain 16 histories each, and
12 F3 extension episodes contain four histories each. Every history has its
own document key and subject session. The episode, rather than each history
sharing it, is the unit for election and recovery timing.

For each property, the related operations bracket the fault transition:
W1/fault/R1 for RYW, W1/R1/fault/R2 for MR, W1/fault/W2 for MW, and
R1/fault/W2 for WFR. MR requires R1 to return its acknowledged version-1 seed
write; otherwise the history is a precondition miss. In the four C1/C6 RYW/MW
signature cells, F3 starts before W1: launch the independent writes
concurrently and retain those routed to the former primary during the transient
partition, observe the majority-side election, then issue R1 or W2 on that side.
This captures a possible C1 `w:1` rollback and the contrasting C6
majority-write wait or failure. The independent observer checks all three
members after healing or restarting the failed node. The primary analysis
retains any acknowledged write later rolled back after convergence.

For F2, after each history's pre-fault operation, the fault controller stops
the primary and the runner waits for a new primary before issuing the
post-fault operation. It deliberately sends no subject request during this
election barrier. F2 therefore measures scheduled-operation success and
election duration separately; it does not measure continuous request-level
availability during election.

Eight controlled repetitions support reproducible-behavior comparisons, not a
precise estimate of a true violation probability. The report states counts and
denominators and keeps scheduled-operation success separate from
completed-history consistency.
