\section{Consistency Configurations}

\subsection{MongoDB consistency mechanisms}

RQ1 varies read concern, write concern, and causal-session setting.
Read concern governs which data state a read may return; write concern governs
the acknowledgement condition for a write. In a causally consistent session,
MongoDB documents combinations of these concerns with different client-centric
guarantees \cite[slides 49 to 53]{cai-lecture-3}
\cite{mongodb-read-concern,mongodb-write-concern,mongodb-read-preference,mongodb-causal-consistency,pymongo-sessions}.

Both causal-session conditions use an explicit PyMongo session. The OFF
condition sets causal consistency to false; it does not omit the session. Each
test schedule selects a read preference and member to create the required
observation. The runner records the requested member and the server that
actually handled each operation; routing is not an independent factor in C1-C8.

These rows explain why C3, C4, and C6 were selected as targets. In
particular, majority read and majority write alone are not treated as a
substitute for the causal-session mechanism when the question concerns a
dependency between operations \cite[slides 49 to 53]{cai-lecture-3}
\cite{mongodb-causal-consistency}.

\subsection{RQ1 predictions}

Before the campaign, we registered which configurations would be tested as
targets for each client-centric property. C3 targets MR and WFR, C4 targets
MW, and C6 targets all four. A targeted history can still be UNAVAILABLE or
INDETERMINATE when the schedule does not return the required value or complete
the dependent operation; those outcomes do not test the prediction. A
completed, decidable VIOLATION would contradict the prediction. For
configurations without a target, the campaign records descriptive outcomes
rather than a prediction test. C5 separates majority concerns from causal
session state, so its concern settings alone are not treated as a causal
session guarantee.

We fixed these predictions before running the campaign. An acknowledgement
does not prove that a write survives recovery:
the independent observer checks the converged state, while the history retains
the acknowledged operation and records any later rollback. The MongoDB
documentation also distinguishes causal sessions and concern combinations,
including the durability condition on majority reads and writes
\cite{mongodb-causal-consistency}.

\subsection{RQ2 fault predictions}

Before the fault campaign, we made four predictions, labelled H2.1 through
H2.4:

\begin{description}
\item[H2.1] A secondary crash should reduce redundancy; operations that remain
routable should not create a new consistency anomaly.
\item[H2.2] A primary crash should appear as an election interval and possible
temporary unavailability rather than as a completed invalid history.
\item[H2.3] Isolating the former primary should expose differences between
weak and majority write acknowledgement, including rollback of an acknowledged
write on the isolated branch.
\item[H2.4] Majority concerns with causal sessions may turn a would-be
counterexample into a wait or an unresolved operation instead of a returned
stale value.
\end{description}
