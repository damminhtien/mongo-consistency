\section{Introduction}

\subsection{Project objective}

Our experiments measure what one MongoDB client can observe across operations
on replicated data. We test four client-centric properties with registered
schedules, versioned histories, and offline checkers. A completed history that
contradicts a required dependency is a violation. Failed operations and
unresolved effects remain unavailable or indeterminate, not passes. We follow
the course's client-centric definitions \cite[slides 37 to 44]{cai-lecture-3}.

\subsection{Scope}

MongoDB is deployed as a three-data-bearing-member replica set in Docker
Compose. The first experiment, RQ1, uses eight configurations labelled C1
through C8. They vary read concern, write concern, and causal-session setting.
The second experiment, RQ2, tests a secondary crash, a primary crash followed
by an election, and a partition that isolates the former primary from
replication traffic while preserving its client route. It uses C1, C3, C4, and
C6 and reuses matching RQ1 normal controls as its descriptive baseline.

The third question, RQ3, explains representative outcomes using three
instrumented, single-factor contrasts: causal sessions (C5/C6), read concern
(C8/C5), and write concern (C3/C6). These targeted replays complement the
campaign outcome matrices; they do not estimate violation probabilities.

RQ4 is an offline analysis layer over the RQ1 and RQ2 histories. It measures
the client-visible cost of avoiding a completed consistency violation using
observed definitive completion and critical-operation p50/p95 latency. It does
not add a workload or treat the resulting completion rate as formal CAP
availability.

Findings are limited to the recorded software versions, schedules, C1-C8
configuration matrix, and single-host container deployment. We did not measure
production availability or behavior across geographically separated machines.
