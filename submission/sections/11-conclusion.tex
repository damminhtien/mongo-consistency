\section{Conclusion}

We set out to see how MongoDB's consistency settings affect client operations
during normal operation and when replicas fail or lose contact. In the normal
runs, all four checks passed. However, once replicas diverged, weaker settings
sometimes returned stale reads or allowed a later write to run without its
predecessor. With C6, we found no completed counterexample in the tested
schedules. Many reads and writes did not complete, so those histories do not
count as passes.

When a secondary failed, or when we issued calls after a new primary had been
elected, none of the scheduled tests showed a consistency violation. During a
replication partition, however, the behaviour changed. Weaker settings
returned stale or reordered state, while stronger settings often waited or
timed out. As a result, some clients received an inconsistent value, while
others received no result before the timeout. We ran these tests on one Docker
host and did not issue requests during an election. The findings therefore
describe only the schedules and failures we tested; they do not cover
deployments across separate sites.
